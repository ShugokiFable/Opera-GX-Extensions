# _Deploy

One-click install, update, and packaging for every extension in this folder.

## Use it

| Double-click | What it does |
| --- | --- |
| `Install-Or-Update.cmd` | Copies every extension to `%LOCALAPPDATA%\GX-Extensions\<name>`, reports what changed, and reports what Opera GX is actually running |
| `Build-CRX.cmd` | Builds a signed `.crx` per extension with Opera GX's own packer. Drag one onto `opera://extensions` to install or update |
| `Package-Release.cmd` | Install/update plus a versioned `.zip` per extension, for GitHub releases |

Two ways to run an extension, and you can use both at once on different machines:

- **Unpacked** - files live in the deploy folder, updates land on the next
  browser restart. Zero friction while you are actually changing code.
- **Signed .crx** - one file you can hand to someone, or keep for yourself.
  Rebuild after a version bump and drag it in; it updates in place.

Both resolve to the **same extension ID**, because the manifest carries the
public key of the signing key. Develop unpacked, ship the `.crx`, one identity.

## Signed .crx

`Build-CRX.cmd` shells out to `opera.exe --pack-extension`, the browser's own
signer. No third-party tooling, no OpenSSL, no npm.

Each extension has one private key in `_Deploy\keys\<slug>.pem`, generated on
first build and reused forever after. Reusing it is what makes a new `.crx` an
update rather than a second copy of the extension.

To ship an update:

1. Raise `version` in the extension's `manifest.json`
2. `Install-Or-Update.cmd`
3. `Build-CRX.cmd`
4. Drag the new `.crx` from `Packages\` onto `opera://extensions`

**Back up `_Deploy\keys`.** Lose it and every future build installs as a brand
new extension. The key cannot be recovered from a `.crx` or from the browser.

### Who can install a .crx

| Target | Works? |
| --- | --- |
| Your Opera GX | Yes - drag onto `opera://extensions` |
| Someone else's Opera GX | Usually; they may still need Developer mode enabled |
| Chrome / Edge / Brave | **No.** Chromium rejects any `.crx` lacking a Web Store publisher signature (`CRX_REQUIRED_PROOF_MISSING`) |

So `.crx` is the right format for you and for people you hand it to directly. It
is not a general distribution channel. For that you want the Opera add-ons store
(free) or the Chrome Web Store (one-time developer fee) - both also give you
automatic background updates instead of manual drags.

## Packed vs unpacked, and why a copy can look like it did nothing

Every run prints **What Opera GX is actually running**, because copying files
correctly and still seeing the old version is the easy failure here:

| Report | Meaning |
| --- | --- |
| `live (unpacked from deploy folder)` | Updates land on the next restart or Reload |
| `PACKED vX` | Installed from a `.crx`. No folder on disk feeds it - update it with a new `.crx` |
| `unpacked from <path>` | Unpacked, but from somewhere else. Works, but dies with that path |
| `not installed` | Never loaded |

## Adding a new extension

Drop the folder next to the others in `Browser Extention` with a `manifest.json`
inside. It is picked up automatically on the next run, gets its own signing key
on the next `Build-CRX.cmd`, and needs no configuration.

For an extension that lives somewhere else, add its path to `extra-sources.txt`.

## Why it installs to LOCALAPPDATA instead of loading from here

An unpacked extension's ID is derived from its absolute path.

- Loading straight off `Z:\` means the extension breaks whenever that drive is
  not mounted.
- Renaming a source folder (a `-v1.3.0` suffix bump, say) changes the path, so
  Opera treats it as a brand new extension and you lose its settings and its
  place on the toolbar.

The deploy folder name comes from the manifest's `short_name`, so it stays put
across version bumps and folder renames.

## Drift detection

Every extension here exists twice: the loadable copy at the top level and a repo
mirror under `zSources\`. Nothing links them, so editing one silently forks the
pair. On each run the script compares them by content hash and prints exactly
which files drifted and where to copy them.

Build inputs are not mistaken for mirrors: a folder missing the scripts its own
manifest references (NEXUS keeps a `static\` folder of hand-written assets, with
`background.js` and `panel.js` generated by its TypeScript build) is skipped
rather than reported as permanent drift.

## Notes

- Needs only Windows built-ins - PowerShell 5.1, robocopy, Compress-Archive -
  plus Node.js for the one step that derives a public key from a signing key.
- `robocopy /MIR` is used, so the deploy folder is an exact mirror. Do not edit
  files under `%LOCALAPPDATA%\GX-Extensions`; they are overwritten on next run.
- `.git`, `.github`, and `node_modules` are never copied into a deployed
  extension.
